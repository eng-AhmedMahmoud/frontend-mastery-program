Question 1 · the answer

D, E, A, B, C.

D async 50ms→ E async defer 60ms→ A async 300ms→ B defer 200ms→ C defer 300ms
Two rules produce the whole order. async runs the instant its download lands, so the async scripts sort themselves by download time. defer runs after parsing finishes, and deferred scripts keep document order among themselves — which is why B beats C even though they both landed at different times.
E is the trap. When a tag carries both keywords, async wins. defer is only the fallback for browsers that do not support async, and every browser you are shipping to supports async.
Q1 · the answer in full

Give the two rules before the letters, then the letters fall out on their own: async sorts by download time, defer waits for the parser and then keeps document order.

Name the wrong answer out loud — 'async and defer are basically the same, they both mean non-blocking' — and say what it costs in production: the async analytics script runs before the config script that defines its global, and it fails once a week on slow connections and never on your laptop.

On E: both keywords means async. Say it twice; it is the single most missed line in this question.

Q1 · why — the three loading strategies

What the parser does
in each case.

Q1 · the mechanism, one lane at a time

Step 1, the classic script: the parser stops dead, downloads, executes, then resumes. Two stalls, and the download stall is the one that shows up as a blank screen on a hotel wifi connection.

Step 2, async: the download moved off the critical path but the execution did not. Point at the exec block sitting inside the parsing lane and say it out loud — async is not free, it is one stall instead of two, at an unpredictable moment.

Step 3, defer: fetch in parallel, execute after the DOM is complete. This is the default you should reach for, and the only one of the three that guarantees order.

The line at the bottom is the takeaway for module 10: downloading is cheap, executing on the main thread is not.

Question 2 · the answer

D only.

  • AThe render tree contains all the elements from the DOM and the CSSOM.Only the visual ones. <head> and everything under display: none are excluded.
  • BCompositing separates layers based on z-index.Compositing combines layers. z-index affects their stacking order, but it is not what creates them.

On D, connect it forward: the reason the compositor thread matters is question 10. A transform animation is smooth precisely because it never touches the main thread.

Question 3 · the answer

One resolver.
Three name servers.

  1. browser → recursive DNS resolver — where is website.com?
  2. resolver → root name server
  3. root → here is the TLD name server's IP (the one that knows .com)
  4. resolver → TLD name server
  5. TLD → here is the authoritative name server's IP
  6. resolver → authoritative name server
  7. authoritative → here is the website's IP address
  8. browser → now, finally, opens a TCP connection to that IP
Every name server answers one question and refers you onward. Only the recursive resolver chases the chain — which is why it is the only one of the four that keeps a cache.
Q3 · the answer in full

Read the eight lines as a conversation, not a list. The resolver is the assistant making phone calls; the three name servers are receptionists who each know one thing.

Two facts worth saying out loud because they get asked in interviews. There are thirteen root server addresses, not thirteen machines — anycast routing points one address at hundreds of boxes worldwide. And the TTL on a record is what decides how often this whole chain runs again.

Then the bridge to the next question: all of this happened before a single byte of your HTML was requested. That is what a resource hint is buying you.

Question 4 · the answer

D — 4, 2, 1, 5, 3.

4→2→ 1→5→3

Why 4 is first

The function you pass to new Promise — the executor — runs synchronously, right now, on the current call stack. new Promise returns a promise; it does not schedule one.

Why 3 is last

setTimeout for 3 is not called until its microtask runs — which is after the timers for 1 and 5 were already sitting in the task queue. It joins the back of a queue it was late to.

The loop drains the entire microtask queue after each single task. Not one microtask — all of them, including any queued while draining.
Q4 · the answer in full

Lead with the two cards, not the sequence. If they understand that the executor is synchronous and that 3 gets scheduled late, the order is not something they have to memorise.

The word to give them is 'executor'. It has a name, and knowing the name is what stops people saying 'the promise body is async'. The body is not async. Only what comes out of it is.

Then the rule on the key line, and say the second sentence deliberately: all of them, including microtasks queued while draining. That is how an infinite microtask loop freezes a tab, and it is a good interview follow-up to be ready for.

Q4 · why — run it line by line

Eleven steps
to 4, 2, 1, 5, 3.

  1. line 1 — setTimeout(…1) called, callback handed to the timer, then straight to the task queue
  2. line 2 — Promise.resolve() is already settled, so then(…2) is queued as a microtask
  3. line 3 — same again — the callback that will call setTimeout(…3) is queued as a microtask. Nothing timed yet.
  4. line 4 — new Promise(executor) — the executor runs now, synchronously  →  logs 4
  5. line 5 — setTimeout(…5) — callback joins the task queue, behind 1
  6. script ends — the call stack empties. Only now does the event loop get a turn.
  7. microtasks first — run then(…2)  →  logs 2
  8. still draining — run the second microtask: it calls setTimeout(…3), which puts 3 at the back of the task queue — behind 1 and 5
  9. microtasks empty — take one task  →  logs 1
  10. next task —  →  logs 5
  11. next task —  →  logs 3
Console: 4   2   1   5   3 — and 3 is last not because it was slow, but because it was scheduled late.
Q4 · eleven clicks — this is the slide that fixes the question

Slow. One click per line, and read each line as you reveal it. The room follows this far better than a diagram with things flying around.

Question 5 · the answer

Two are about the pipe.
Two are about the payload.

  • dns-prefetch2 — resolves the domain name in the background. Buys you the DNS chain from question 3.
  • preconnect3 — DNS plus the TCP and TLS handshakes. The connection is open and waiting.
  • prefetch4 — downloads a resource you will probably need next, at low priority. The browser is free to ignore it.
  • preload1 — downloads a resource you need now, at high priority. The browser is not free to ignore it.
The split that makes them memorable: dns-prefetch and preconnect open a pipe and fetch nothing. prefetch and preload fetch a payload. And of the second pair, only preload is about the page you are on right now.
Q5 · the answer in full

Give the pipe-versus-payload split first — it collapses four things to remember into two.

Then the priority difference inside each pair. preconnect is dns-prefetch plus the handshakes. preload is prefetch that the browser may not skip.

The warning that belongs here and gets asked in interviews: these all compete for the same bandwidth and the same connection limit. Preconnect to six origins on a mid-range Android and you have made the page slower, not faster. Two or three, for origins you know are on the critical path.

Question 6 · the answer

B — Jane, 102 Main St.

Spread copies one level deep. name is a string, so member2 got its own copy and the later reassignment cannot reach it. address is an object, so what got copied was the reference — both objects point at the same address in memory.
The phrase to keep: a shallow copy duplicates the top-level properties. For anything that is not a primitive, the property is a reference, so duplicating it duplicates the arrow, not the thing the arrow points at.

Fixes that work

structuredClone(member) for a real deep copy. Or copy the nested object explicitly: { ...member, address: { ...member.address } }.

The bug this causes

Two components hold what looks like separate state. One edits a nested field. The other re-renders with a value nobody assigned to it — and there is no line of code to blame.

Q6 · the answer in full

The distinction is not shallow versus deep, it is primitive versus reference. Say it that way. name behaved 'correctly' only because strings are copied by value; nothing about spread treated it specially.

Give structuredClone as the modern answer — it is in every browser now and it handles Dates, Maps and cycles, which the JSON round-trip does not.

The card on the right is the reason this is in a hiring diagnostic at all. This is a real bug, it has no stack trace, and people lose whole afternoons to it.

Question 7 · the answer

Four are clocks. One is
a sum. One is not time at all.

  • TTFB4 — the server responds and the first byte lands. Not the last byte. The response is still streaming.
  • FID1 — how long the first click waited for a busy main thread before it could even be processed.
  • TTI5 — the first moment the main thread stays quiet long enough to be reliably interactive.
  • TBT2 — every millisecond the thread ran past 50, added up. A total, not a timestamp.
  • CLS6 — how much the layout moved under the reader. A score, with no unit and no clock.

Q7 · why — TTFB, and everything that happens before it

The first byte,
not the last one.

DNS, TCP and TLS all finish before the request is even sent — and all three are on the clock. TTFB stops at the moment the first byte of the response arrives, because that is the moment the parser can start work. The rest of the response is still on the wire behind it.
Q7 · TTFB — five clicks, and the last one is the point

Build the network row left to right and name each segment as it lands: name lookup, connection, handshake, request out. Four things the server has not even seen yet.

The marker is the whole slide. Say it plainly: TTFB is not 'the server finished'. It is 'the first byte landed', and a response normally streams in after it.

Then the consequence, which is the interview answer: TTFB is the only vital that is mostly not your JavaScript. It is DNS, connection, handshake, server think-time and distance to the user — which is why the fixes are a CDN, a warmer cache and an earlier connection, not a smaller bundle.

Q7 · why — FID, and the 50ms line

The click that arrives
while the thread is busy.

FID measures the wait, not the handler. And it is a fragile number: click a moment earlier and it is near zero, click a moment later and it is 300ms — same page, same code. If the user never interacts, there is no value at all. That fragility is exactly why INP replaced it.
Q7 · FID — four clicks, and one honest caveat

Draw the thread first and define the long task out loud: over 50 milliseconds. Tell them the Performance panel draws these with a red corner and that this is the bar they are hunting for in module 10.

Click two puts the user's click inside the 325ms task. Say what actually happens: the event is real, it is queued, and the thread cannot look at it. Two hundred milliseconds feels short written down and feels broken in the hand.

The caveat is the part worth marks in an interview: FID depends on when the user happened to click, and it does not exist at all if they never click. That is why it was replaced — say it here, and the INP slide six clicks later lands as a fix rather than a new acronym.

Q7 · TTI and TBT — six clicks on one timeline

Deliberately one figure for two metrics, because they are two readings of the same trace and people who learn them apart end up swapping them.

TTI first: find the last long task, require five clean seconds after it, and stamp the marker at the start of that window. Say the retrospective bit out loud — TTI can only be known after the fact, which is why it is a lab metric and not a field one.

Then TBT: subtract 50 from each long task and add up what is left. 40, 5, 104, total 149. The arithmetic is trivial and doing it live is what makes it stick.

If someone asks why 50: it is roughly the point where a queued input stops feeling instant. It is a chosen threshold, not a law of physics.

Q7 · why — CLS, the one with no clock

Distance × impact.
No unit, no milliseconds.

Same bug, two scores. The banner moved everything, so its impact fraction is 1 and the distance goes straight through. The filter bar left the header alone, so 40% of the screen never moved and the score drops by two thirds. Reserve the box before the content arrives — width and height on images, min-height on slots, aspect-ratio on embeds — and both scores go to zero.
Q7 · CLS — four clicks, and the only vital with no clock

Lead with the shape: two fractions multiplied, so the result is a fraction. That is why it has no unit and why the threshold — 0.1 for good — looks like nothing until you know what it is a fraction of.

Distance fraction: how far the content moved, as a share of the viewport's largest side. Impact fraction: how much of the viewport was involved. Both are per shift, and the score is the worst burst of shifts in a session window.

Work the two examples out loud, because the arithmetic is the lesson: 0.22 × 1 is a fail and 0.13 × 0.6 is a pass, and the difference is only how much of the screen the shift touched.

Close on the fix, which is never a JavaScript fix: reserve the space. Dimensions on images, min-height on ad and banner slots, aspect-ratio on embeds, and never inject above existing content after paint.

Q7 · why — INP, and what it fixed about FID

Click, to the frame
that answers it.

INP watches every click, tap and key press for the life of the page and reports roughly the worst one. It replaced FID as a Core Web Vital in March 2024, for the reason this figure shows: a fast handler that then triggers an expensive re-render is a slow interaction, and FID scored it as perfect.
Q7 · INP — five clicks, and the modern answer

Build it in the order the browser does it: the thread is busy, the click waits, the handler runs, then layout, paint and composite before anything is visible. Point out that only the last of those puts pixels on screen.

The comparison is the whole slide: FID measures the first segment and stops. INP measures the whole bar. A handler that returns in two milliseconds and then sets state that re-renders a thousand rows is a bad interaction and a perfect FID.

Say the date — March 2024, INP replaced FID as a Core Web Vital — because it is the kind of detail that reads as current rather than memorised, and interviewers notice.

Forward-link to module 10: the fix is the same family as TBT. Yield before the expensive work, keep the update small, and let the browser paint the acknowledgement first.

  • TBT“How much of that time was the page frozen?”   ms, summedThe lab stand-in for INP. Cut long tasks into short ones and it falls.
  • CLS“How much did the page move under me?”   a scoreDistance × impact. Reserve the space before the content lands.
  • INP“How long from any interaction to the frame that answers it?”   msThe one Google scores you on today. Wait + handler + render, worst case, whole session.
If you remember one thing: TBT is what you can measure in the lab, INP is what the user actually feels — and they move together, because both are killed by the same long tasks.
Q7 · close — the one-line version of each

This is the recall slide. Read each acronym as a question rather than a definition, because a question is what an interviewer is really asking when they say 'walk me through Core Web Vitals'.

Land the last line: TBT is the lab proxy, INP is the field truth, and both come from the same long tasks. That single sentence answers most follow-up questions about performance in a screening round.

Five directives,

  • must-revalidate2 · Serves stale content while validating the cached response with the origin server.
  • no-store3 · Does not cache any part of the request or the response.
  • private4 · Validates the cached resource with the origin before using it, even if it is still fresh.
  • stale-while-revalidate5 · Prevents caching on shared caches.
Q8 · read the definitions carefully, they are close on purpose

Definitions 1, 2 and 4 all contain the word 'validate'. That is the whole difficulty. The differences are: even if fresh, only when stale, and while serving stale.

Almost everybody puts no-cache on definition 3. The name is genuinely misleading and it is worth letting them make the mistake before you correct it.

32 / 50
Question 8 · the answer

The one with
the wrong name is no-cache.

  • no-cache4 — revalidate before every use, even while fresh. It caches. It just never trusts the cache on its own.
  • must-revalidate1 — use it freely until it goes stale; once stale, revalidate before serving.
  • no-store3 — never written down anywhere. This is the one people mean when they say no-cache.
  • private5 — the browser may cache it, a CDN or proxy may not.
  • stale-while-revalidate2 — serve the stale copy instantly, refresh it in the background.
no-cache does not mean do not cache. It means do not use the cache without asking first. If you want nothing written down, the directive is no-store — and that is the one you want for anything user-specific or financial.
Q8 · the answer in full

Lead with the naming trap, because it is the only part of this question people carry into production. no-cache caches. no-store does not.

Then the three revalidation timings as one sentence each: no-cache asks every time. must-revalidate asks once it is stale, and the user waits for the answer. stale-while-revalidate does not make the user wait at all.

private is the odd one out and belongs with a CDN diagram: your browser may keep it, the shared cache in front of your server may not. Dashboards, account pages, anything keyed to a user.

Q8 · why — no-cache, and the ETag handshake

Two round trips,
one of them nearly free.

An ETag is a hash of the file. The browser sends the one it holds; the server compares and either says nothing changed in a few hundred bytes, or sends the new file.
Q8 · three clicks — first request, revalidation, change

The point of click two is the size difference. A 304 is still a network round trip, so it is not free, but it moves a few hundred bytes instead of a few hundred kilobytes. That is the deal no-cache is offering.

Click three is why ETags exist at all. The server, not the browser, decides whether the hash still matches. The browser only ever reports what it is holding.

If asked about Last-Modified: same handshake, one-second resolution, and it loses to ETag whenever both are present.

Q8 · why — who waits, and for how long

Fresh, stale,

Q8 · the timing difference, in two bars

Row one: the moment the max-age expires, every user pays a round trip. That is must-revalidate, and it is the honest default when correctness matters.

Row two: the same expiry, but the stale copy still goes out immediately and the refresh happens behind it. Nobody waits. The window is finite — after max-age plus the stale window, it behaves like must-revalidate again, which is the part people forget.

The judgement call to say out loud: this is only correct when being briefly out of date is harmless. Job listings, yes. An account balance, absolutely not — that one is no-store.

Q9 · a question about which decade you learned this in

Question 9 · the answer

D — collected on
the next cycle.

Why not A

A cycle only leaks under reference counting, which counts how many arrows point at an object. Two objects pointing at each other never reach zero. No engine you are shipping to uses that.

Why not B

Setting a variable to null does not free anything. It removes one arrow. Collection happens when the garbage collector next runs, on its own schedule — which is why the answer says can be, not is.

Modern engines use mark and sweep: start at the roots — the global object, the current call stack — and mark everything you can reach. Anything unmarked is swept, cycle or no cycle. Reachability from a root is the only test.
Q9 · the answer in full

The one idea: the question is not 'is anything pointing at it', it is 'can you get to it from a root'. Those sound the same and are completely different. Two objects on a desert island point at each other all day and are still unreachable.

Be precise about 'can be'. Nothing is freed at the moment you write null. The collector runs when it runs, and on a busy tab that may be a while.

Where this still bites in real code: a listener you never removed, a setInterval you never cleared, a closure held by a module-level array. Every one of those is reachable from a root, which is exactly why it never gets collected.

Question 10 · the answer

A and D.

  • Awidth → layout, paint, compositeChanging a box's size can move everything around it. The browser has to measure again.
  • Bopacity → paint, compositeComposite only. The element is promoted to its own layer and the layer's alpha is changed. No pixels are redrawn.
  • Cbackground-image → compositePaint and composite. Nothing moves, so no layout — but those pixels have to be drawn.
  • Dleft → layout, paint, compositeA positioned offset is still geometry. Same cost as width.
  • Etransform → paint, compositeComposite only. The layer is moved, not redrawn. This is why translateX and left look identical and cost nothing alike.
Q10 · the answer in full

The pipeline runs in one direction, so there are only three possible answers per property: all three stages, the last two, or the last one. Nothing can paint without compositing afterwards.

The pair that matters for a whole career is D and E. left and translateX move an element the same distance on screen and cost completely different amounts. One re-measures the page on every frame, on the main thread. The other changes a number on a layer the GPU already holds.

Say the caveat once so nobody quotes this back as absolute: browsers promote layers on their own judgement, and a property that is composite-only while animating may not get its own layer when it is set once.

Question 11 · the answer

A, C, G, F, D, E.

A→C→ G→F→ D→E B never runs

Three phases, not two

Capture down from the root, target at the element itself, bubble back up. Listeners default to the bubble phase, which is why the ones without true all fire on the way back.

Why E still runs

stopPropagation stops the event moving to the next element. Every remaining listener on the current element still fires. To stop those too you need stopImmediatePropagation.

Q11 · the answer in full

Give the three phases first, then the letters read themselves off the diagram.

The card on the right is the part almost nobody gets. stopPropagation is about elements, not about listeners. D calls it and E — a sibling listener on the very same element — still runs. If you want E silenced, the method has a longer name.

The practical note: capture-phase listeners are rare but they are the only place you can intercept an event before a child gets it, which is how a modal traps focus or a drag layer swallows a click.

Q12 · the trap, stated properly

Only one of these
brackets is free.

:where(…)

Always zero. Whatever is inside it, however specific, contributes nothing. This is the whole reason it exists — it is the escape hatch for library defaults that must be easy to override.

:not(…)

The colon itself is free, but its argument counts. :not(.promo) adds one to the class column, exactly as .promo would.

:has(…)

Same rule as :not(). Free bracket, and the most specific thing inside it counts in full.

If you have heard that :not() is ignored by the specificity counter, that is worth unlearning today. It takes the specificity of its most specific argument. :where() is the only one of the three that is genuinely free, and knowing that difference is a real answer to a real interview question.
Q12 · the correction — say it as a correction

This is worth a full beat because the wrong version is widely repeated. :not() and :has() pass through the specificity of their argument. Only :where() is zero, and that is the entire point of :where().

The practical version, which is what they will actually use: wrap your library or reset selectors in :where() so consumers can override them with a plain class, instead of fighting you with !important.
