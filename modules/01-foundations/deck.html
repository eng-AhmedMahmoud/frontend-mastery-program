The same bug, answered at three levels

One search box.
Three different engineers.

// JUNIOR — "add a debounce"
<input onChange={debounce(handleSearch, 300)} />   // a brand-new debounce every render

// MID — "…and keep its identity stable across renders"
const search = useMemo(() => debounce(handleSearch, 300), [])
useEffect(() => search.cancel, [search])        // cancel the pending call on unmount

// SENIOR — "…and two responses can still land out of order"
const seq = useRef(0)
async function run(q) {
  const id = ++seq.current
  const res = await fetch(`/api/jobs?q=${q}`, { signal })
  if (id !== seq.current) return                  // a stale answer — drop it
  setResults(await res.json())
}
All three "work" on a fast laptop. Only the third one survives a reviewer asking what happens on a slow connection.
L3 · the ladder in code — the slide that proves it

Walk the three blocks slowly, and say out loud that all three work on your laptop. That is the trap: the junior version is not broken, it is unreviewed.

Point at the two annotations in the mid block — memoised identity and cleanup on unmount — and say that this pair is what most mid-level candidates are missing. Then point at the sequence check in the senior block: it is four lines, and it is the difference between an offer band.

Do not teach debounce here. If a student asks how it works, answer 'module 3, and you will write it yourself.' Protect the lesson's runtime.

Format 2 · the JavaScript utilities round

Empty file.
Forty-five minutes.

// "Write debounce. Then add cancel. Then tell me what happens to `this`."
// No library. No autocomplete. They watch you type.

export function debounce(fn, wait) {
  let timer, lastArgs, lastThis

  function debounced(...args) {
    lastArgs = args; lastThis = this          // the follow-up they are waiting for
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(lastThis, lastArgs), wait)
  }
  debounced.cancel = () => { clearTimeout(timer); timer = undefined }
  debounced.flush  = () => { if (timer) { clearTimeout(timer); fn.apply(lastThis, lastArgs) } }
  return debounced
}
This exact function is module 3, exercise 1. You will write it from an empty file with the tests already red — which is the only rehearsal that transfers.
L4 · format 2 · run the empty file

If you can, type the first four lines of this live rather than revealing them. The lesson is not the implementation — it is that an empty file with someone watching is a different skill from writing the same code alone.

Point at the `lastThis` line and name the follow-up question by name: 'what happens to this?' Candidates who wrote an arrow function cannot answer it, and that is the entire purpose of the follow-up.

Close by connecting forward: this is module 3, exercise 1, with the tests already red.

Lesson 5 · the diagnostic

Pen and paper.
No pausing to search.

  • Write your answer down before I give minea half-formed answer still counts as a mark
  • One point per question you got substantially rightgenerous about wording, strict about mechanism
  • Twelve questions, one sitting, nothing looked upa question you can only answer with a search is one you cannot answer in an interview

Your score is not a verdict

It is an address. Every question you miss points at a specific module number — and that module already has a lesson written for exactly that gap.

Most experienced React developers score between 4 and 7. That is the normal result, not the bad one.

The failure mode

Watch four modules in a weekend, feel excellent, write nothing. Two weeks later you can name every concept and implement none of them.

This is the single most common way to finish a program like this and be exactly where you started. It feels like progress the entire time, which is why it works on everyone.

One module a week, with the exercise done, beats four modules watched.
