Property 1 of 2 · size

Who decides how big the box is?

Intrinsic

You set no rule. The content decides. Longer text → taller box. This is the default and it is what makes HTML resilient.

Restricted

You set a size, or the parent caps it. Parent shrinks → box shrinks. This is where overflow bugs are born.

Most "why is my layout broken on mobile" bugs are an intrinsic box that someone made restricted, in one breakpoint, and forgot.
Teach

Give a concrete pair: a card that grows with its text vs a card with height: 220px. Ask which one survives a translated string. Arabic text is on average longer than English — this lands with this audience.

Property 1 of 2 · size

The same box, two widths

box-sizing: content-box

width: 300
padding: 20 * 2
border: 2 * 2
------------------
on screen: 344px

You must add the layers up yourself — in CSS and again in JavaScript.

box-sizing: border-box

width: 300
padding: included
border: included
------------------
on screen: 300px

The number you wrote is the number on screen. Only margins are still outside.

This is why every real codebase starts with *{ box-sizing:border-box }. It turns layout math into one number instead of five.
Teach

Say the interview version out loud: "content-box means width applies to the content only; border-box means width applies through the border. We set border-box globally so measurement in JS matches measurement in CSS."

Property 2 of 2 · type

Block-level boxes

  • Takes 100% of the parent's widthalways — even with one short word in it
  • Height comes from the contentintrinsic, unless you restrict it
  • Stacks top to bottom
  • Creates or joins a block formatting context
Loose text that is not inside a tag still gets a box — the browser wraps it in an anonymous block box. There is no such thing as unboxed content.
Teach

The anonymous box is a great interview detail. It explains why a stray string inside a flex container becomes a flex item.

Inline boxes behave like text

width / height

Ignored. Setting them does nothing.

vertical margin

Ignored. Horizontal margin still works.

vertical padding

Paints, but does not change the line's height.

Exercise · read it like the browser does

Line by line, context by context

<html>
  <body>
    <h1>Jobs</h1>
    <ol>
      <li style="display:inline-block">…</li>
    </ol>
    <section style="display:flex">
      <div><span>Cairo</span></div>
    </section>
  </body>
</html>
tagwhat it does
htmlcreates the root block context
bodyjoins it — no special display
h1 · oljoin it too
liinline-block → creates a new block context
sectionflex → creates a flex context
divbecomes a flex item, and creates a block context for its children
spancreates an inline context
The rule: an explicit display creates a context. Everything else just joins the one it is standing in.
Exercise

Do this on the whiteboard, not on the slide. Ask the room for each line before you reveal it. The div row is the one people miss — it is a flex item to its parent and a block container to its children at the same time.

Two trees, merged

The five phases, and what they cost

Where the frame budget goes

phasewhat happensruns onblocks the main thread?
JavaScriptyou change the DOM or a styleCPUyes
Stylere-match selectors, rebuild the subtreeCPUyes
Layoutrecompute position and size of every affected boxCPUyes
Paintdraw pixels into bitmapsGPUno

The bill · measured in Chrome DevTools · Layers panel

Every promoted layer costs VRAM

8.7 MB
the first graphic layer — you pay this once, on every page
+0.5 MB
each extra layer you promote with a 3D transform
~100 MB
a 200-item list where somebody promoted every row
GPU memory is not yours — it belongs to the whole system. Overrun it and the OS starts swapping, and the page you were "optimising" becomes the one that freezes.
Add will-change: transform to a list item and it looks free in DevTools on a desktop. It is not free on the phone the student is being interviewed about.
Demo

The judgement call

Promote a widget. Never promote a page.

Worth a layer

One element that moves constantly: a drag handle, a sticky header, a chart tooltip, a video, an open modal. High activity, small count, short-lived.

Not worth a layer

Every row of a list. Every card in a grid. Anything static. Anything you promoted "just in case" and never measured.

Both mistakes exist. Using the CPU when you could use the GPU drops frames instantly. Using the GPU everywhere runs you out of memory slowly. Prefer the GPU — but count the layers.
Teach

Answer the question a student always asks: "isn't transform always better?" Yes, for the animation. No, if you promoted 300 elements to get it. Measure in the Layers panel, then decide.

Say this in the interview

Four sentences that end the question

1 · The browser builds a DOM from HTML and a CSSOM from the stylesheets, and merges them into a render tree of everything that is visible.

2 · Changing the DOM or a geometric style forces a reflow — style and layout run again on the CPU, and that blocks the main thread.

3 · Paint and composite run on the GPU, so animating transform or opacity skips layout entirely.

4 · Elements can be promoted to their own graphic layer for that, but each one costs GPU memory — so I promote the widget that animates, not the list around it.

Delivery

Record this slide slowly and in Arabic, then repeat the four sentences in English — this is the one paragraph students will memorise for the "why" round.
