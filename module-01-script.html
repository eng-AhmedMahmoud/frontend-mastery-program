03

Delivering it in Arabic

The script below is written in English prose designed to be spoken in Arabic. Short sentences, no idioms, no wordplay. This section fixes the vocabulary so all 14 modules sound like one person.

Six rules, applied everywhere

  • The technical noun stays English. The sentence stays Arabic. «الـ event loop مش هيشغّل تاسك جديدة قبل ما الـ microtask queue تفضى.» Never build an Arabic sentence around a translated term the student will never see in a codebase.
  • Gloss once, then drop the gloss. The first time a term appears, give one Arabic sentence explaining it, then use the English term for the rest of the program. Do not re-explain in module 7 something glossed in module 2.
  • Never translate an API name, a metric name, an error message or an identifier. Read useDeferredValue, Cache-Control: no-store and INP in English, at English speed, then explain in Arabic.
  • Numbers and units in Arabic and English respectively. «مية وتمانين millisecond», «اتنين ونص seconds». Never «مللي ثانية».
  • Read code left to right, in English, then narrate in Arabic. Do not reorder a code line into Arabic word order — the student is looking at the line.
  • One dialect, one register. Egyptian Arabic, spoken, no MSA lecture voice. But keep the technical register formal enough to re-use in an interview.

Terms we deliberately do not translate

If a term is what the interviewer will say out loud in English, the student must own the English. Translating these creates a student who understands the concept and freezes in the room.

05

The diagnostic — question bank and spoken answer key

This section is the script for lessons 5 and 6. Twelve questions, ours, written for this program — each one chosen because it foreshadows a specific later module and because the wrong answer is a common, respectable, confident wrong answer.

How it runs on camera
  • Read the question, then stop talking. A twenty-second countdown appears on screen. Do not fill the silence — the silence is the product.
  • Answer in sixty to ninety seconds. Full answer, no hedging, no "we'll cover this later" as a substitute for an answer.
  • Name the common wrong answer out loud. Students who gave it need to hear that it is common, not stupid. This is what keeps them watching.
  • Close with the address. One sentence: "this is module 8." Then move. No transition, no summary.
  • Scoring is binary and generous. If they got the mechanism, it counts, even if the wording was loose. Say that before question 1.
The instruction block, spoken once before Q1 (lesson 5): «Pen and paper. Twelve questions. Do not pause the video to search — searching will give you a right answer and a wrong picture of yourself. Write a short answer for each one, even if you are guessing. Mark yourself at the end. Nobody sees this but you, and the score is not a judgement — it is an address.» ⇄
Part 1 · Lesson 5 · The browser and the language
Q1

Three script tags, three behaviours

→ Module 2
Here are three scripts in the <head> of the job board. In what order can they execute, and which one can delay the first paint?
<head>
  <script src="/analytics.js"></script>
  <script defer src="/filters.js"></script>
  <script async src="/ads.js"></script>
</head>
Answer. analytics.js is guaranteed first, and it is the only one that can delay the first paint: the parser stops at that tag, downloads the file, executes it, and only then continues building the DOM. filters.js is deferred — it downloads in parallel and executes after the HTML is fully parsed, just before DOMContentLoaded. Deferred scripts keep document order among themselves. ads.js is async — it executes the moment its download finishes, so it can land second or third, before or after the deferred script, and there is no order guarantee between two async scripts at all. So the only certainty is: analytics first, filters last-ish, ads whenever.
The common wrong answer: "defer and async are the same thing, both are non-blocking." They are both non-blocking for the parser. They differ on when they run and on whether order survives — and that difference is what breaks a page in production, when the async analytics script runs before the config script that defines its global.
Where this is paid off: M2 the critical rendering path, parser blocking, resource hints (preload, preconnect, modulepreload) · M10 removing sequence chains to improve FCP.
Q2

Two ways to move a card 200 pixels

→ Module 2
You need to slide a job card down by 200 pixels, animated. Option A sets element.style.top = '200px'. Option B sets element.style.transform = 'translateY(200px)'. Which is cheaper, and name the pipeline stage each one re-enters.
Answer. The browser's pipeline is style → layout → paint → composite. top re-enters at layout: the browser recomputes geometry for that element and potentially for everything after it in the flow, then repaints, then composites. transform on a promoted element re-enters at composite only: no layout, no paint, and the work can happen on the compositor thread — which means the animation keeps running smoothly even while the main thread is busy with JavaScript. That is why "animate transform and opacity, nothing else" is a rule and not a style preference.
The common wrong answer: "transform is faster because it uses the GPU." Half right and it will not survive one follow-up question. The GPU is the consequence; the mechanism is that you skipped two pipeline stages and left the main thread.
Where this is paid off: M2 reflow vs repaint, compositing layers, what makes an animation cheap · M10 animation cost, INP, yielding the main thread.
Q3

Output order inside a click handler

→ Module 2
What does this log, in what order — and at which point in that sequence does the browser get a chance to paint a frame?
applyButton.addEventListener('click', () => {
  console.log('1');
  setTimeout(() => console.log('2'), 0);
  Promise.resolve().then(() => console.log('3'));
  console.log('4');
});
Answer. 1, 4, 3, 2. The handler runs to completion first — 1 then 4. When the call stack empties, the event loop drains the entire microtask queue before anything else, so 3. Only then does it take the next task from the task queue, so 2. The paint opportunity comes after the microtask queue is empty and before the next task — which means a long chain of microtasks blocks rendering exactly as badly as one long synchronous function. setTimeout(fn, 0) does not mean "now"; it means "at the earliest, in a future task."
The common wrong answer: 1, 4, 2, 3 — because "setTimeout zero runs immediately and promises are slow because they're async." Promises are not slow. They are earlier.
Where this is paid off: M2 the event loop: call stack, tasks, microtasks, rendering frames · M3 callbacks → promises → async/await, and building Promise.all from scratch.
Q4

Three good numbers and one bad one

→ Module 10
The job board reports LCP 1.8 s, CLS 0.02, INP 480 ms. (a) What is INP actually measuring? (b) The slow interaction is typing in the filter box, which re-renders a list of 500 cards. Which of these three fixes INP: debouncing the input, wrapping the card in React.memo, or putting the filter value through useDeferredValue?
Answer. (a) INP — Interaction to Next Paint — measures the time from a user interaction to the next frame the browser actually paints, and it reports close to the worst interaction of the whole page visit, not the average. Over 200 ms is "needs improvement"; 480 ms is a page that feels broken. (b) All three help, but only one addresses the mechanism. The main thread is blocked rendering 500 cards before it can paint, so: useDeferredValue (or startTransition) lets React paint the keystroke immediately and render the list at lower priority — the interaction gets its frame. React.memo lowers the cost per card, but you still do 500 of them in one blocking pass. Debounce just delays the same long frame, and now the input feels laggy on purpose. The production answer is deferred value plus virtualization, so you render twenty cards, not five hundred.
The common wrong answer: "Debounce it." Debounce is the reflex answer for every input problem in frontend, and it is the right answer roughly a third of the time. Knowing which third is the job.
Where this is paid off: M10 Core Web Vitals, INP, yielding the main thread, React transitions and deferred values · M7 list virtualization implemented by hand · M5 what a render costs.
Q5

Two loops, two outputs

→ Module 3
What does each loop print, and what is the one-sentence explanation for the difference?
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j), 0);
// ?
Answer. The first prints 3 3 3. The second prints 0 1 2. var is function-scoped, so all three callbacks close over the same binding; by the time the timers fire, the loop has finished and that one binding holds 3. let creates a fresh binding for every iteration, so each callback closes over its own. The sentence to remember: a closure captures the binding, not the value. This is not trivia — it is exactly the mechanism behind the stale-closure bug in useEffect with a missing dependency: your effect captured the binding from the render it was created in, and that render's values never change.
The common wrong answer: "Both print 0 1 2, because the callback gets the value at the time it was created." That is a completely reasonable mental model. It is also the one that will cost you an hour of debugging a React hook one day.
Where this is paid off: M3 execution contexts, scope chains, closures · M5 hooks and the closure trap.
Q6

A method that loses its object

→ Module 3
What happens on the last line, why, and give two different fixes.
const api = {
  base: '/api',
  url(path) { return this.base + path; }
};

const url = api.url;
console.log(url('/jobs'));   // ?
Answer. It throws — Cannot read properties of undefined — in a module or in strict mode, or quietly returns "undefined/jobs" in sloppy mode. this is decided at call time by how the function is called, not at definition time by where it was written. Called bare, there is no receiver, so this is undefined. Two fixes: const url = api.url.bind(api), or wrap it — const url = (p) => api.url(p) — because an arrow function has no this of its own and takes the surrounding one. A third, if it were a class: define the method as an arrow class field. And this is precisely why every React class component tutorial had a constructor full of .bind(this) before arrow functions became normal.
The common wrong answer: "It logs /api/jobs, because url is still the same function." It is the same function. It is not the same call.
Where this is paid off: M3 this, prototypes, classes and what they compile to · M5 event handlers and referential identity.
Part 2 · Lesson 6 · Types, React, architecture
Q7

Same object, two verdicts

→ Module 4→ Module 6
Why does the first assignment error and the second one not — when the object is identical?
type Job = { id: string; title: string };

const a: Job = { id: '1', title: 'Frontend Engineer', remote: true };  // error

const draft = { id: '1', title: 'Frontend Engineer', remote: true };
const b: Job = draft;                                              // fine
Answer. TypeScript is structurally typed: it compares the shape of a type, not its name. draft has everything Job requires, so it is assignable — extra properties are simply not TypeScript's problem. The first line hits a separate, deliberately narrow rule called the excess property check, which only applies to a fresh object literal assigned directly to a typed target. It exists to catch typos like titel, not to enforce exactness. The consequence that matters in production: types cannot stop extra or wrong data arriving at runtime from an API. For anything crossing the network boundary you need a schema — Zod — not an interface.
The common wrong answer: "TypeScript objects must match exactly." They must match structurally and at minimum. Believing in exactness is how people end up fighting the compiler instead of using it.
Where this is paid off: M4 structural vs nominal typing, excess property checks, narrowing · M6 typing props and spread props, schema validation with Zod at the API layer.
Q8

memo that does nothing

→ Module 5
JobCard is wrapped in React.memo. The parent JobList re-renders because something unrelated changed. How many cards re-render, and why?
const JobCard = React.memo(function JobCard({ job, onApply }) { /* … */ });

function JobList({ jobs }) {
  return jobs.map(job =>
    <JobCard key={job.id} job={job} onApply={() => apply(job.id)} />
  );
}
Answer. All of them. memo does a shallow comparison of props; onApply is a brand-new function object on every render of JobList, so the comparison fails for every card, every time. The memo bought you nothing and added the cost of the comparison. Fixes: give onApply a stable identity with useCallback and pass the id to the handler instead of closing over it — onApply={apply} with the card calling onApply(job.id). The principle: memoization is about referential stability, and one unstable prop defeats it entirely. React 19's compiler removes most of this hand-work, which changes when you should reach for it — but not what it does.
The common wrong answer: "None — that is what memo is for." Half the memo calls in real codebases are decorative for exactly this reason.
Where this is paid off: M5 the render model, anatomy of a re-render, what React 19's compiler changed · M10 memoization and when it actually pays.
Q9

The note that moved to the wrong job

→ Module 5
The list is keyed by index. The user types a private note into the input inside the third row, then sorts the list by date. What happens to the note, and why?
{jobs.map((job, i) => <JobRow key={i} job={job} />)}
// JobRow renders <input placeholder="private note" />
Answer. The note stays in position three and now sits next to a completely different job. React matches elements between renders by key within a parent. key={i} tells React "the third element is the third element" — so after sorting, React reuses the same component instance and the same DOM node, and only swaps the props. The uncontrolled input's value lives in that DOM node, so it stays. Use key={job.id}. Index keys are safe only for a list that never reorders, never has an insert or delete in the middle, and holds no state — which is a much smaller set of lists than people assume.
The common wrong answer: "The note disappears" or "React re-creates the rows." Neither. React is doing exactly what you told it. That is what makes this bug so quiet.
Where this is paid off: M5 reconciliation and keys, why lists break · M7 controlled vs uncontrolled components and where component state actually lives.
Q10

It works with a mouse

→ Module 7
This ships and nobody complains for six months. Name five things you lost.
<div className="btn" onClick={apply}>Apply</div>
Answer. One: focus — a div is not in the tab order, so a keyboard user cannot reach it without tabIndex. Two: activation — onClick fires on click, not on Enter or Space, so even if they reach it they cannot press it. Three: the accessibility tree role — a screen reader announces "Apply" as plain text, not "Apply, button", so the user does not know it is actionable. Four: the disabled state — no disabled attribute, so no semantics and no automatic event blocking; you now have to guard it manually and remember to. Five: form behaviour — inside a <form> there is no submit and no Enter-to-submit. Plus the free focus ring, :focus-visible defaults, and Windows High Contrast Mode. Adding role="button" tabIndex={0} and two keydown handlers gets you back to roughly where <button> started. That is the whole argument for semantic HTML: it is not styling, it is behaviour you would otherwise reimplement badly.
The common wrong answer: "Add role="button" and it's fine." Role fixes the announcement. It does not add focus, keyboard activation, or the disabled state — ARIA changes what is announced, never what the element does.
Where this is paid off: M7 keyboard paths, focus management, ARIA roles and live regions, the component gauntlet · M2 semantic HTML and the accessibility tree.
Q11

Whose state is it, and whose response is that

→ Module 8
(a) Four pieces of state on the job board — the list of jobs from /api/jobs, the text in the search input, whether the filter drawer is open, and the selected filter values. Which of them belong in useState? (b) The user types "react" quickly. Two requests are in flight. The response for "rea" arrives after the response for "react". What does the user see, and what is the fix?
Answer. (a) The list of jobs is server state — you do not own it, it can go stale, it needs caching, revalidation, a loading state and an error state. That belongs in a query cache, not useState. The drawer being open is genuine client state: useState, correct. The search text and the selected filters are client state that should live in the URL — so refresh, back button, and a shared link all reproduce the same view. Roughly: one of the four is really a useState. (b) The user sees results for "rea" sitting under the word "react" — a race condition, not a caching bug. Fixes, in order of how a senior would say them: key the request by its input so the cache stores one entry per query and a stale response cannot overwrite a fresh one; abort the previous request with AbortController; or, at minimum, track a request id and ignore anything that is not the latest. Debounce reduces how often this happens. It does not prevent it.
The common wrong answer: "Put it all in useState and add a debounce." This is the single most common architecture in a junior codebase, and the single most common reason a mid-level candidate does not get the senior offer.
Where this is paid off: M8 server vs client state, TanStack Query caching and invalidation, URL search params as state, race conditions, optimistic updates.
Q12

Four pages, four strategies

→ Module 9→ Module 11
The job board has four surfaces: the marketing homepage; the listings feed with filters; a single job page that must rank on Google; and the company's applicant dashboard behind a login. (a) Pick a rendering strategy for each and justify it in one clause. (b) Then: name the first three things you would ask before designing the feed.
Answer. (a) Homepage → static (SSG). It changes weekly, it must be instant, and it can sit on a CDN. Single job page → SSG with ISR, or a cached server render. It has to be in the HTML for the crawler and for the social preview card, but there are forty thousand of them and they change — so generate on demand and revalidate rather than rebuilding the world. The feed → server-render the first page for the LCP, then fetch on the client when filters change; filters live in the URL so a shared link reproduces the view. Dashboard → behind auth, fully personalised, zero SEO value: client render, or a server component with no caching — pick whichever gives the simpler auth story. The rule underneath: "which rendering strategy" is really three questions — who is it for, does a crawler need it, and how often does it change. (b) Before designing the feed, ask: who the users are and at what scale (a hundred jobs or forty million?), what the feed must do besides scroll (filters, saved searches, a live "new jobs" badge, offline?), and which constraints are already fixed (SEO, mobile web versus app, an API you do not control). Asking before drawing is the R in RADIO, and it is the first move of the design round.
The common wrong answer: "Next.js, server-side render everything." Which is a technology, not a decision — and the follow-up question ("why?") is where the round is actually scored.
Where this is paid off: M9 CSR / SSR / SSG / ISR / streaming and how to choose, server vs client components · M11 RADIO — requirements before architecture · M10 LCP and TTFB.

How to Study This Program

08:00
On-screen goal: The student has the repo cloned, one failing test running on their own machine, and knows exactly what to do when they get stuck — before they get stuck.
Spoken script

Hook · 0:00–0:30 There is one way to take this program that guarantees you learn almost nothing, and it is the most comfortable way. You watch all fourteen modules. You nod. Everything makes sense while it is on screen. You do not write a single line of code. At the end you feel educated — and then you sit a real interview and cannot implement debounce from an empty file. Understanding and being able to are different skills, and only one of them gets tested. So here is how this program is actually built to be used.

Beat · the three branches · 2:30 Every coding exercise in this program ships as three git branches. Same exercise, three states.

Start. module-3/utils/start — the scaffold plus failing tests. No hints, no TODOs, nothing telling you the answer. This is the branch where the learning happens, and it is the branch most people skip.

Guided. module-3/utils/guided — the exact same failing tests, plus TODOs, hints, and the reasoning written into the comments. Not the answer — the thinking that leads to the answer.

Solution. module-3/utils/solution — finished and commented. And I want to be specific about what this branch is for: it is for diffing against yours, not for reading first. git diff module-3/utils/solution and read the differences. Where our two solutions disagree is the actual lesson, and it is a lesson you cannot get by reading working code.

Beat · the twenty-minute rule The rule that makes those three branches work: twenty minutes stuck before you open guided. Not five. Twenty.

And I want to explain why, because "struggle more" sounds like discipline theatre. When you are stuck and searching your own memory for the answer, your brain is doing something it does not do while reading — it is building the retrieval path you will need later. If you read the hint at minute three, you get the answer and no path. It will feel like you learned it. Two weeks later, in an interview, there is nothing to retrieve.

And there is a second reason, which is more practical. In the real interview, nobody hands you a hint at minute three. You will be stuck in front of someone, on a clock. The skill of being stuck productively — narrating what you know, writing the smallest failing case, saying "let me start with the simplest version" out loud — is a skill you can only practise while stuck. Twenty minutes alone with a failing test is that practice.

Beat · what to do when stuck · four steps When you hit the wall, before you touch the guided branch, run these four in order.
One: read the failing test again, slowly. It is a specification. Most of the time the test tells you the thing you forgot.
Two: write the smallest possible case. Not the full feature — one input, one expected output, and get that green.
Three: say the problem out loud in one sentence, as if to another person. «أنا عايز الـ function ماتنفّذش غير لما يعدّي وقت من آخر call — والمشكلة إني مش عارف أمسك الـ timer بين الـ calls.» ⇄ Half the time you solve it in that sentence. That is not a trick, that is the same mechanism the interview round is testing.
Four: now open guided. You earned it.

Module seven, the components: the filter drawer, the dropdown, the tabs, the autocomplete, the toast — built from scratch, no libraries. Module eight, the data layer: the query cache, optimistic apply, filters that live in the URL. Module nine, the rendering strategy. Module ten, the performance budget and the tests. And then module twelve is not a build week — it is an assembly week. You will not start from an empty folder. Most of that product already exists, on branches you wrote yourself.

Beat · the rhythm · 45 s Practically: one module a week, three sessions. Watch the lessons in one or two sittings, do the exercise in the third, and finish the exercise before the next module drops. If you fall behind on exercises but keep watching, stop watching. Go back. A person who has done six modules properly is dramatically further along than a person who has watched fourteen.

Speed: first pass at normal speed. Second pass, when you come back for the interview prep, at one and a half. Do not watch a module you have never seen at double speed — you will finish faster and retain nothing, and I would rather you refunded than did that.
