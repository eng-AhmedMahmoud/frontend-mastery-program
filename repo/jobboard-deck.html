The shape

Mini-projects that add up to a product

Module 12 isn't a new project. It's the assembly of eleven things the student already built — which is why finishing it is realistic.

Why one product

Pure mini-projects leave a student with nothing to point at in an interview. A single big project is where people stall in week three. This is the middle: each module ships something finishable, and they are all slices of the same app.

The model

Every exercise exists three times

<stage>/startScaffold, types, fixtures and the failing tests. Bodies throw Not implemented. No hints. This is where the student begins.
<stage>/guidedThe same tests, plus numbered TODOs and the reasoning behind each. The escape hatch — not the answer key.
<stage>/solutionFinished, green, with NOTES.md on the trade-offs and what an interviewer will push on.

The tests are byte-identical across all three. Only the amount of implementation changes — that's what makes red → green feel earned.

Named by module and video, the same way every repo in the course is: module-3/v4-utils/start, with m3-v4-end tagging the solution so a student who fell behind can jump straight to it.

Three branches

Struggle first, hint second, compare third. The order matters: a hint read before the struggle is worth almost nothing. And because the tests never change between the three, the student is always working against the same contract.

On naming: the stage sits under its module and video, so the branch list sorts into the order the program is recorded in. Video numbers are pending each module's lesson map, so today the branches read module-3/utils/start — the v4 segment and the end tag land with the map.

How they stay in sync

Only one branch is written by hand

// in the solution — ordinary comments, no build step
// #hint 1 The timer id lives in the closure — that's what lets one call cancel the previous one.
// #region solution
  let timeout: ReturnType<typeof setTimeout> | undefined
  …the real implementation…
// #endregion

$ pnpm stage:publish module-3/utils   # solution → guided → start
$ pnpm stage:verify  module-3/utils   # prove all three behave

Hand-editing a derived branch is how three versions silently diverge. Here you can't: they're regenerated and force-pushed every time.

Generation

Write the solution. A script strips it twice — once keeping hints as TODOs for the guided branch, once removing them for the starter. Test files and fixtures are never touched. Authoring order is the reverse of the student's order.

The bug that shaped the tooling

A stage must not un-teach the last one

Stage 7 branches from stage 3's solution, so the first run of the stripper blanked the utilities too — and m07/start shipped with a broken debounce. The tests failed, but for the wrong reason.

// stage.config.json — on every stage branch
{ "stage": "module-7/autocomplete", "strip": ["src/components/autocomplete"] }

$ git checkout module-7/autocomplete/start && pnpm test
PASS (39)  ← the utilities, still solved from m03
FAIL (15)  ← the autocomplete, the actual work
Scoping

Worth telling students about: this is what "the second use case reveals the real design" looks like. The first stage worked fine with a naive stripper. The second one broke it, and the fix — declaring scope per stage — is the thing that makes twelve stages possible.

The guardrail

CI checks the starter fails

$ pnpm stage:verify module-7/autocomplete
✓ module-7/autocomplete/solution     expected pass, got pass
✓ module-7/autocomplete/guided       expected fail, got fail
✓ module-7/autocomplete/start        expected fail, got fail
✓ test files identical across all three

A starter branch whose tests accidentally pass is a lesson with nothing to do in it. That gets caught by a machine, not by a student's support message three weeks after launch.

CI

Every push runs typecheck, then asserts the branch behaves the way its name promises: solution green, start and guided red. The same script runs locally before publishing a stage.

Stage · module-7/autocomplete

Type → debounce → suggestions → arrow keys → Enter. Focus never leaves the input; aria-activedescendant does the moving.

The gauntlet

This is the single most-asked "build this live, no libraries" question in frontend interviews. Five skills collide in it and most candidates get three.

Why this component

Five skills, one question

#SkillHow candidates fail it
1DebouncingA request per keystroke
2Race conditionsThe older response lands last and overwrites the newer results
3KeyboardNo wrapping, Enter submits the form, the caret jumps
4ARIA comboboxMoving real focus into the list — breaks typing entirely
5State honestyLoading, empty and error all rendered as “nothing happened”

Number 2 is the one that separates mid from senior — and the one that ships to production and then produces a bug nobody can reproduce.

Five skills

Ask a candidate to build an autocomplete and you're testing all five at once. That's why it's the most common question, and why it's the module 7 centrepiece.

The test that matters

Two responses, out of order

it('ignores a slow response that arrives after a newer one', async () => {
  const slow = deferred<JobSuggestion[]>()   // resolved by hand
  const fast = deferred<JobSuggestion[]>()

  await user.type(input, 'react')          // request 1 → slow
  await user.type(input, ' engineer')      // request 2 → fast

  fast.resolve([reactEngineer])            // newer answers first
  slow.resolve([senior, midweight])        // older lands last…

  expect(screen.getAllByRole('option')).toHaveLength(1)  // …and is ignored
})

Sequence numbers keep the UI correct. AbortController stops the wasted network. Interviewers want both — they solve different problems.

Race

You cannot test this with timers alone; you need promises you resolve by hand. Teaching that technique is half the lesson — most students have never controlled resolution order in a test before.

Filters & optimistic apply

Filter → the list refetches and stale requests abort → Apply flips instantly, then confirms. Optimistic UI, without lying to the user.

Data layer

Right now this is hand-rolled fetching with an AbortController and a sequence number. In module 8 it is replaced by TanStack Query and the filters move into the URL — and the students can diff the two and see exactly what a data library is actually doing for them.

Day one, module one

The whole workflow is three commands

$ git checkout module-3/utils/start        # red: 39 failing
$ pnpm test:watch                     # work until green
$ git diff module-3/utils/solution -- src/ # compare, don't just check

# stuck on one function? pull only its hints:
$ git checkout module-3/utils/guided -- src/utils/debounce.ts

Taught once in module 1, used for the rest of the program. It's also the git workflow they'll use at work — branches, diffs, and comparing your approach against someone else's.

Workflow

Deliberately plain git. No custom CLI, no platform lock-in. If they leave the course they keep the repo and it still works.
